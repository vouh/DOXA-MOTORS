DOXA MOTOR SOLUTIONS - CAR HIRE MANAGEMENT SYSTEM
STAGED IMPLEMENTATION PLAN AND CURRENT-SYSTEM AUDIT
Audit date: 31 July 2026

PURPOSE
This document converts the Solution Design Document (SP-DOXA-2026-001) into an actionable implementation plan. It also records what is already present in the current Doxa repository.

STATUS KEY
[IMPLEMENTED]      Feature and core workflow exist in the repository.
[PARTIAL]          Some code/UI/data structures exist, but important work remains.
[NOT IMPLEMENTED]  No usable implementation was found.
[VERIFY]           Code exists, but production credentials, infrastructure, or end-to-end testing are required.

IMPORTANT AUDIT NOTE
This is a source-code audit, not confirmation that every database migration, provider credential, cron schedule, or production environment is live. An item is only called fully implemented when its main UI, persistence, and business workflow are present. Provider-dependent items are marked PARTIAL/VERIFY until tested end to end.

======================================================================
STAGE 1 - FOUNDATION, DATABASE, AUTHENTICATION AND SECURITY
Priority: Critical; complete before production use
======================================================================

Already present
[IMPLEMENTED] Next.js App Router, React, TypeScript, Tailwind CSS and branded admin UI.
[IMPLEMENTED] Prisma/PostgreSQL configuration and relational car-hire models.
[IMPLEMENTED] Zod schemas for client, owner, vehicle, booking, condition, penalty, payment and expense inputs.
[IMPLEMENTED] Supabase authentication/session utilities and login screens exist.
[PARTIAL] User accounts and access concepts exist, but current roles are legacy organization roles (ADMIN, EXECUTIVE, TREASURER, etc.), not the agreed Director, Receptionist, Yard Staff and Accountant model.
[PARTIAL] Staff & Role Management screen exists, but it uses hard-coded in-browser sample data; edits are not persisted.
[NOT IMPLEMENTED] Consistent server-side role checks on car-hire server actions, admin pages, export, cron and M-Pesa endpoints.
[PARTIAL] Audit-log infrastructure exists, but car-hire changes such as penalty settings, commissions, dispatch and settlement are not consistently written to it.

Implementation work
1. Define persistent car-hire roles and a permission matrix: Director, Receptionist, Yard Staff and Accountant.
2. Persist staff accounts and permissions; remove hard-coded demo staff/roles.
3. Protect every /admin car-hire page, server action and API route server-side.
4. Record actor IDs on bookings, condition checks, payments, expenses and configuration changes.
5. Add audit entries for sensitive actions and configuration changes.
6. Review storage policies so IDs, licences, logbooks and agreements are private.
7. Add rate limiting/input hardening to login, lookup and payment endpoints.

Acceptance criteria
- Unauthorized users cannot read or mutate car-hire data by directly calling an action or URL.
- Each agreed role can perform only its approved tasks.
- Staff and permission changes survive refresh/restart.
- Sensitive changes identify the actor and time.

STAGE 2 - CLIENTS, OWNERS, VEHICLES AND PRIVATE DOCUMENTS
Priority: High
======================================================================

Already present
[IMPLEMENTED] Client database model and registration UI with name, phone, email, ID/passport, licence, expiry, address, next of kin, employer, second contact and status.
[IMPLEMENTED] Client search by phone or ID/passport.
[IMPLEMENTED] Client suspension and activation.
[IMPLEMENTED] Owner model and registration UI, including commission type/value and recurring deduction.
[IMPLEMENTED] Vehicle register, owner assignment, vehicle type, daily rate and operational status.
[IMPLEMENTED] Insurance and inspection expiry records can be created with a vehicle.
[PARTIAL] Database fields exist for client ID/licence files and owner ID/logbook/agreement files, but the car-hire forms do not upload or manage these files.
[PARTIAL] Vehicle image/document file URLs exist, but complete private upload/view/replace/delete workflows are missing.
[NOT IMPLEMENTED] Edit/detail workflows for existing clients, owners and vehicles are incomplete or absent.
[NOT IMPLEMENTED] Licence-validity enforcement during booking/dispatch.

Implementation work
1. Add secure Supabase Storage upload controls for client ID, driving licence, owner ID, logbook, signed agreement, vehicle image and certificates.
2. Add authorized signed-link viewing and safe replacement/deletion.
3. Add client, owner and vehicle detail/edit screens with validation and audit history.
4. Prevent booking/dispatch for suspended clients or expired licences.
5. Add uniqueness/conflict messages for duplicate phone, ID, licence and registration values.

Acceptance criteria
- Required records and private document copies can be created, viewed and updated by authorized staff.
- National ID/phone lookup returns the correct client quickly.
- Suspended clients and invalid licences cannot proceed to dispatch.

STAGE 3 - BOOKING, DISPATCH, EXTENSION, RETURN AND CHARGES
Priority: High
======================================================================

Already present
[IMPLEMENTED] Booking creation with client, vehicle, start/end time and daily rate.
[IMPLEMENTED] Automatic base-charge/day calculation.
[IMPLEMENTED] Overlapping active booking prevention.
[IMPLEMENTED] Booking references and status lifecycle.
[IMPLEMENTED] Dispatch condition check with dents, fuel, odometer and component status.
[IMPLEMENTED] Dispatch changes vehicle status to hired.
[IMPLEMENTED] Hire-extension calculation and persistence exists in server logic.
[PARTIAL] Hire extension has server logic but no clear control in the bookings UI.
[IMPLEMENTED] Return condition check and vehicle check-in.
[IMPLEMENTED] Configurable penalty rules with grace period, hourly/daily rate and cap.
[IMPLEMENTED] Penalty snapshots/trace data store rule, minutes late, amount and calculation notes.
[IMPLEMENTED] Check-in applies lateness penalty and returns the vehicle to available status.
[PARTIAL] Condition photo storage exists in the model but upload/capture UI is missing.
[PARTIAL] Booking-created confirmation is required but is not queued when a booking is created.
[PARTIAL] Dispatch message is queued, but Director dispatch/payment/fleet-count notification is missing.
[NOT IMPLEMENTED] Client invoice, receipt and hire-agreement generation.

Implementation work
1. Expose hire extension in the booking UI and validate vehicle conflicts after extension.
2. Add condition-photo upload at dispatch and return.
3. Queue booking-confirmed messages and Director dispatch summaries.
4. Generate printable/downloadable hire agreement, invoice and receipt.
5. Add booking cancellation and safe vehicle-status recovery.
6. Add full booking detail/history view, including checks, extensions, penalties and payments.

Acceptance criteria
- A booking can complete the full reserved -> dispatched -> returned lifecycle.
- Charges and penalties are reproducible from stored values.
- Extensions update charges and expected return time without creating conflicts.
- Required agreements and transaction documents can be produced.

STAGE 4 - PAYMENTS, M-PESA AND OWNER SETTLEMENT
Priority: High; depends on client Daraja/Paybill details
======================================================================

Already present
[IMPLEMENTED] Manual CASH, M-PESA, BANK and OTHER payment recording.
[IMPLEMENTED] Paid and outstanding balances are calculated from completed payments.
[PARTIAL/VERIFY] Car-hire M-Pesa STK Push route and Daraja client exist; real credentials and live/sandbox tests are required.
[PARTIAL/VERIFY] M-Pesa callback finds pending car-hire payments and marks them completed/failed; callback security, idempotency and real-provider behavior require hardening/testing.
[NOT IMPLEMENTED] Paybill/C2B reconciliation for payments initiated outside STK Push.
[PARTIAL] Payment-received messages are queued for manually recorded payments, but the STK callback does not queue the same confirmation.
[IMPLEMENTED] Vehicle/owner expense entry and expense attribution.
[IMPLEMENTED] Owner settlement calculation supports percentage/fixed commission, recurring deduction and itemized expenses.
[IMPLEMENTED] Monthly payout generation and persisted draft payout records.
[PARTIAL] Owner statements are displayed as rows but no detailed statement document/report exists.
[NOT IMPLEMENTED] Approve payout, mark payout paid, save payment reference and notify owner.

Implementation work
1. Add authenticated STK controls to booking/finance UI and restrict amount to the valid outstanding balance unless override is authorized.
2. Harden callback idempotency, amount/reference validation, logging and failure recovery.
3. Implement Paybill C2B confirmation/validation and unmatched-payment reconciliation.
4. Queue payment confirmations for successful callback payments.
5. Build payout approval/payment workflow and immutable settlement details.
6. Generate individual owner statements and payout reports; notify owner after payment.

Acceptance criteria
- STK and Paybill payments reconcile once against the correct booking.
- Failed/unmatched transactions are visible and recoverable.
- Owner gross earnings, deductions, expenses and net pay are explainable.
- A payout can be approved, paid, documented and communicated.

STAGE 5 - AUTOMATED SMS, EMAIL, SCHEDULER AND BULK MESSAGING
Priority: High; depends on approved templates/providers/Sender ID
======================================================================

Already present
[IMPLEMENTED] Message-log/queue database model and communication audit page.
[IMPLEMENTED] Events queue dispatch, return and manually recorded payment messages.
[IMPLEMENTED] Cron logic queues hire-ending-soon notices within two hours.
[IMPLEMENTED] Cron logic marks late dispatched bookings overdue and queues overdue notices.
[IMPLEMENTED] Cron logic finds vehicle documents expiring within seven days and queues Director alerts.
[PARTIAL] Resend email integration exists elsewhere in the repository, but the car-hire message queue has no delivery worker.
[NOT IMPLEMENTED] SMS gateway/Sender ID delivery integration for car-hire messages.
[NOT IMPLEMENTED] Worker that sends QUEUED messages and updates SENT/DELIVERED/FAILED status.
[PARTIAL] Current logic chooses email instead of SMS when email exists; the SDD workflow says SMS + email for events, with email used where available.
[NOT IMPLEMENTED] Bulk SMS to clients and owner broadcast messaging.
[NOT IMPLEMENTED] Retry policy, provider delivery callbacks and duplicate-send protection across all triggers.
[VERIFY] Production cron schedule and CRON_SECRET configuration.

Implementation work
1. Confirm channel rule with client, then generate SMS plus email where required.
2. Add approved templates with variables and versioning.
3. Implement email/SMS queue worker, provider adapters, retries and status updates.
4. Add provider delivery webhooks where supported.
5. Add bulk client and owner broadcast composer with preview, audience filters and audit log.
6. Schedule and monitor the cron endpoint in production.

Acceptance criteria
- Every required trigger sends the approved message through the correct channels exactly once.
- Failed deliveries are visible and retryable.
- Bulk sends require permission and show recipient count/preview before submission.

SUMMARY OF CURRENT POSITION
======================================================================

Strongest implemented areas:
- Core relational data model.
- Client, owner and vehicle registration.
- Booking/dispatch/check-in lifecycle.
- Charge, penalty, balance and owner-settlement calculations.
- Basic Director dashboard and finance views.
- Initial M-Pesa STK/callback and scheduler logic.

Highest-risk missing areas:
- Persistent car-hire RBAC and consistent server-side authorization.
- Private document upload/management.
- Actual queued-message delivery and SMS integration.
- Paybill reconciliation and complete payout payment workflow.
- Required PDF/Excel reporting and contractual documents.
- Data migration tooling and comprehensive tests.
- Production-provider/deployment verification.

This plan should be updated after each stage by changing feature statuses and attaching test/UAT evidence.
